## 1. 已改：`_cap_model.set_ckpt` 的推理缓存失效

**位置**：`.local-8b/_cap_model.py:46`（唯一共享改动）。

**旧行为**：

```python
for m in adap:
    m.A.data.zero_();  m.B.data.zero_()
...
    m.A.data.copy_(A.cuda());  m.B.data.copy_(B.cuda())
```

**新行为**：写入改为 `with torch.no_grad(): m.A.copy_(...)`，并在末尾对所有 adapter 加 `m._cache_key = None`。

**为什么必须改（四条证据，缺一不可）**：

1. `LoRALinear.forward` 的推理快路径把缓存键定在 `(id(A), A._version, id(B), B._version, …)`，且命中 `_b_is_zero` 时直接 `return y`（`m110_alllinear.py:72-85`）。
2. `.data.copy_()` / `.data.zero_()` **不递增** `Parameter._version`。实测（CPU，无模型）：
   `start 0 → .data.zero_() 0 → .data.copy_() 0`；改用 `no_grad: p.copy_(...)` 则为 `0 → 1`。
3. 后果是「第一次前向时的状态被永久缓存」。因此**任何在同一进程里先跑过 base 臂、再换 LoRA 的评测，LoRA 臂会逐字返回 base 的输出**——不报错、不掉速、`sum(|B|)` 仍然非零，只是看起来「这一臂弱」。
4. 本轮实测复现：三臂同进程跑，`L_auto_delta` 与 `L_auto` **20/20 逐字相同**（`nonzeroB=248/358`）；同一 checkpoint 单臂新进程跑是 **11/20**。

**影响面**：所有 `from _cap_model import load, set_ckpt` 的脚本 —— `_cap_bench.py`、`_e17/_e18/_e19/_e20/_e21/_e22/_e23` 的评测脚本、`_p2_probe.py`、`_persona_probe.py`。

**回滚**：把 `set_ckpt` 恢复成 `.data.zero_()` / `.data.copy_()`，并删掉末尾的 `_cache_key` 循环。本仓库无版本控制，回滚只能照本节还原。

**为什么不在调用方修**：调用方有七八个脚本，漏一个就重新引入静默错误；而且「换权重」这个动作本身就该负责失效缓存。

**验证**：修后重跑同一四臂（`_e24_auto_probe_v2.json`，不经任何本地补丁），与修复前用本地补丁得到的逐臂分数**完全一致**：`L_auto 3/20`、`L+R 7/20`、`L+Δ 11/20`、`L+R+Δ 15/20`。

## 2. 已审计：#1 有没有污染已归档读数

**判据**：该 bug 的唯一可检测签名是「第 i+1 臂与第 i 臂逐字相同」（缓存只会回放**上一个**状态，不会回放更早的）。因此只需检查每个 JSON 内**相邻臂**的生成文本是否相同。

**方法**：`_audit_arm_identity.py`（只读），对 `.local-8b/_*.json` 中含 ≥2 臂的文件，取每臂 `scenario_rows`/`cap_rows`/`rows` 的 text 拼串做 sha1，比较相邻臂。

**结果**：

| 文件 | 臂数 | 结论 |
|---|---:|---|
| `_cap_bench.json` | 22 | 全臂互异 ✅ |
| `_e21_eval.json` / `_v1` / `_v3` | 6 / 5 / 2 | 全臂互异 ✅ |
| `_e22_probe.json` | 7 | 全臂互异 ✅（`delta_only 7/20 ≠ ledger_only 2/20`，说明当时确实应用上了） |
| `_e22_nodom_probe.json` | 2 | 全臂互异 ✅（LoRA 臂排第一，天然安全） |
| `_e23_cap.json` / `_e23_dfy_probe.json` | 2 / 3 | 全臂互异 ✅ |
| `_persona_probe.json` / `_mem_probe_30*.json` | 7 / 13 | 全臂互异 ✅ |
| **`_e24_dbg_two.json`** | 2 | **命中 `L_auto==L_auto_delta`** —— 这是我为证伪该 bug 故意制造的现场，保留作为证据 |

**CI 类文件**（无逐条文本，只有 KLD）用第二条判据：LoRA 臂若被缓存吞掉，其相对 ref 的 KLD 会**恰为 0.0000**。全部文件的全部臂 KLD 均非零且互异（如 `_e23_wiki_ci` p2 `0.0047` / dfy `0.0034`；`_e21_wiki_ci` v1 `0.0003` / v2 `0.0002`）。

**结论**：归档未受污染。**不需要重跑任何历史臂。**

## 5. 只提不改：三处会影响结论的表述

1. **「Δ 扛规则」这句撤回，方向未定。** 我本轮一度得出「规则进上下文比进权重更值」，但那一组数据来自一个**含评测字段枚举**的契约（见 §3.1）。去掉枚举后：

   `L 3/20 → L+R 6/20 → L+Δ 10/20 → L+R+Δ 11/20`，即 **Δ 贡献 +7、R 只贡献 +3、两者叠加 +1 且不显著**（vs `L+Δ` `(3,2) p=1.0`）。原先「改成账本+规约卡+权重三件」的建议不成立，撤回。是否值得多带 350 tok 的 R，要等第二轮会话（E26b）才能判。

2. **能力电池 n 混用**（24/64/96 三种臂在同一 JSON 里），任何跨臂比较都必须带 `n`。未改。
3. **`PWSH_OPS_RULES_DOC` 含人工修正过的规约**（如 `python -m unittest discover -s ..\tests -v`），而自动抽取会把**过期版**一并保留（`R_auto` 抽到的是会话早期的 `-s tests`，导致 `P03` 失败）。这说明手写规约隐性修正过一处；自动抽取要补一条「被纠正过的规约只保留最新版」。未改，作为 E24 Step 2 的契约修订项——但同样要警惕：这条也是看了 `P03` 才想到的，应先在第二个会话上验证。
