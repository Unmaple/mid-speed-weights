## 优先修改的问题

### R01 成本模型混淆了计算阶段与自变量

**位置：P.1 摘要，P.2 §1.2、§1.4，P.5 表 2 与 §3.4。优先级：高。**

摘要将注入的每个载体 token 计为下一 episode 的 O(L)，正文反复说参数载体只付费一次。该写法没有区分一次性写入、prefix prefill、后续 decode、KV 驻留和每次执行 LoRA 的矩阵乘。表 2 自己已经承认 Δ 有逐次额外矩阵乘，因此“只付费一次”只能限定为写入，不能涵盖总开销。P.3 又写与真实摘要处于相同 token budget，P.5 却明确说双方没有共同成本单位；两个表述应统一。

建议定义历史长度 n、摘要长度 k、保留上下文长度 u、后续生成长度 m，并将 rank 另记为 a，避免与压缩比 r 混用。在标准稠密注意力、固定网络宽度和层数的简化模型下，k 个缓存前缀 token 对 m 次 decode 的增量注意力工作量可写为 O(km)，每个 decode token 的增量为 O(k)；额外 prefill 另计。未合并 LoRA 的额外工作量约与 `m × Σ_l a(d_in,l+d_out,l)` 成正比，其相对 n 固定，但会随使用次数增加。具体缓存、注意力结构及实现可改变常数与部分项，须写清假设。

可保留的结论是：“固定大小 adapter 不占用文本窗口，其每 token 额外计算相对历史长度不增长。”当前没有共同成本测量，不能从此直接推出总成本更低、只付一次费或已达到工程盈亏平衡。

### R02 11 MiB 与 rank 64、四层、FP32 的组合不一致

**位置：P.2、P.3 的预算说明；P.5 §3.1；P.6 §4.2。优先级：高，需以实际 checkpoint 核定。**

论文同时声明 down_proj、层 60—63、rank 64、A/B 均为 FP32、载体约 11 MiB。公开 [Qwen3.8-27B 配置](https://huggingface.co/Qwen/Qwen3.8-27B/raw/main/config.json) 给出 hidden_size=5120、intermediate_size=17408。若冻结 revision 采用这些维度，则：

```text
参数量 = 4 × 64 × (5120 + 17408) = 5,767,168
FP32 权重字节 = 5,767,168 × 4 = 23,068,672 = 22 MiB
BF16 权重字节 = 5,767,168 × 2 = 11,534,336 = 11 MiB
```

因此 11 MiB 恰对应 BF16，不对应上述 FP32 驻留权重。若论文计量的是 BF16 序列化文件，应明说“磁盘载体 11 MiB，运行时 FP32 权重 22 MiB”；若实际运行的 rank、层数或维度不同，则修正设置描述。公开 main 配置不代替实验冻结 revision，最终请用实际 tensor 的 shape、dtype、numel 和 element_size 逐项汇总。训练峰值还要另计梯度、优化器状态、激活和教师张量。42 MB 设计预算也应给出投影数、精度和同一计算口径。

### R03 对 Doc-to-LoRA 的概括与原论文直接冲突

**位置：P.3 §2.2 末尾至 P.4 开头。优先级：高。**

本文把相关方法族概括为上下文在其生命周期中仍保留于窗口、参数只是副本，据此区分自身“文本消失后由参数替代”的问题。但 [Doc-to-LoRA 原论文 §3—4](https://arxiv.org/html/2602.15902v1) 明确描述后续查询无需原始上下文；其 needle 评估中，目标模型仅收到查询，不直接获得原始上下文。因而不能把原始上下文是否移除用作针对该工作的区别。

建议改为：承认已有工作已研究移除上下文后的参数化推理；本文更具体的差别在于压缩触发时点、同一冻结模型的分布监督、session 生命周期，以及真实摘要预算扫描下的受控测量。哪些是组合设计、哪些是新测量，应分别陈述。

同时，[TMEM 原论文 §3—4](https://arxiv.org/html/2606.04536v1) 确实在预算触发点抽取 QA、在线更新 LoRA，并在一个 episode 内累计更新；因此将其列为近邻是合理的。当前稿应更准确地区分“触发时点已有先例”和“监督通道/测量协议不同”。这并非要求本预印本重现全部方法。

### R04 固定载体大小不能推出固定保真度下的容量优势

**位置：P.2 §1.1、§1.4；P.3 §1.5；P.5 §3.4。优先级：高。**

文本从“固定摘要上限”推进到维持保真度时 |S| 必须随 |H| 增长，而 Δ 是常数。后半句只说明配置固定，尚未证明固定 Δ 在历史增长时能保持保真度。两种固定精度、固定大小载体都存在容量上限。现有主实验在 H20 上改变摘要预算，不是以多种 |H| 检验固定 Δ 的容量曲线；也未展示同一 session 连续多次 compaction 的信息保持。

P.3 对后训练的二分也过强：session-local fine-tuning 仍可泛化，可删除性不排斥泛化；跨历史迁移本身不必然说明载体设计失败。应以任务相关保留、非相关干扰和生命周期约束定义目标。

建议把相关段落降为待验证假设。现版贡献集中于“单次边界的参数写入、条件分布拟合和摘要预算交叉”，无需为发布初步预印本立即补终身记忆实验。

### R05 交叉点方向写反，且不应声称必然相交

**位置：P.7 §6.2；P.8 图 1 图注。优先级：高，直接可修。**

当压缩比 r 从 19.8 增大到 309.8 时，表 6 的 SR KL 从 0.0946 增至 0.3286，图 1 蓝线也上升。但正文与图注均写曲线随压缩比下降。应改为“随压缩比增加，SR 的 KL 上升”，或明确“fidelity 下降”，避免把 KL 与保真度方向混同。

RD 不读取摘要只能说明该扫描中 RD 水平线固定，不能推出 SR 一定单调或一定相交。现有数据支持的是：在一个固定 H20、adapter、题池和摘要策略下，256 与 128 token 两个已测预算点的配对差异符号相反。建议以此报告一个观测到的换向区间；[77.5,154.9] 是预算扫描的区间，不是 r* 的 95% 置信区间。

### R10 Cost 小节没有测工程成本，漂移也不等于损害

**位置：P.1 摘要；P.7 §6.3。优先级：中。**

§6.3 实际报告的是无关问题上的输出分布漂移 0.025874，对比加入摘要的 0.016631/0.015966。KL 是变化幅度，不自动表示任务损害，也不是写入时长、推理延迟、吞吐或峰值显存。P.3 又称“real likelihood cost”，但这里展示的是分布 KL，而非 NLL 退化。

### R11 一个数量级错误和两类数学记号需修正

**位置：P.5 §2.7、§3.1；P.7 §6.1、§6.3、§7.1。优先级：中。**

- 人脑神经元写为 `8.6×10^11`，而所引 [Azevedo 等原论文摘要](https://gwern.net/doc/psychology/neuroscience/2009-azevedo.pdf) 报告约 86.1 billion，即 `8.61×10^10`，相差十倍。可直接改正或删去与当前实验关系较远的类比。
- `Δ=Σ_l B_l A_l` 把安装在不同网络层的局部矩阵当作一个全局矩阵求和。更准确地写 `Δ={Δ_l}_{l∈L}`、`Δ_l=B_lA_l` 和每层的 `W'_l=W_l+Δ_l`，在输出算子中定义 session adapter 集合。
- §3.1 明确说裸 R 只表示 tail、指标只比较模型状态，后文仍写 `KL(R || R+Δ)`、`KL(T || R)`，并将 R 当均值指标。统一改用 R0、RD 及明确的分布下标；读者不应自行猜测这一省略。

## 修改顺序与可以延期的工作

**本轮发布前处理，不需要新增大规模实验：**

- [ ] R01：重写成本定义与摘要措辞，区分写入和每次使用。
- [ ] R02：以真实 checkpoint 计算 shape/dtype/字节数，统一 11 MiB、22 MiB、42 MB 口径。
- [ ] R03：更正 Doc-to-LoRA 的无上下文推理描述，精确收窄与 TMEM 的差异。
- [ ] R04：将固定容量长期保真与连续压缩能力降为待验证假设。
- [ ] R05：修正图注/正文曲线方向，删除必然相交，补聚类敏感性。
- [ ] R06—R07：修正非显著结果解释，补 ρ、阈值和辅助结果的运行来源。
- [ ] R08—R09：补现有实验协议、摘要干预及复现包的定位方式。
- [ ] R10—R12：区分漂移与损害，修神经元数量及符号，统一贡献表述。

**可以留待下一版本，只要当前稿不作相应强结论：** 独立金标准的任务表现、真实历史、多次连续 compaction、不同模型、多个训练/采样种子、强压缩基线复现、广泛跨历史泛化、完整工程盈亏平衡实验。

建议结论段围绕已有数据：在一个冻结 27B 模型、四个合成历史和固定教师路径上，边界训练的 session-local adapter 能降低部分历史相对 tail-only 的教师分布 KL；一个 H20 历史的摘要预算扫描出现比较方向换向；较宽摘要预算仍明显优于固定 adapter；这些结果尚不说明语义记忆、任务收益、长期容量优势或部署总成本更低。
